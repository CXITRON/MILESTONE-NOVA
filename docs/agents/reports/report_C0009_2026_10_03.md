## Title

C0008 독립 재검증과 배포된 Worker `/v1/lyrics` 502 수정

## Summary

Codex가 이어서 작성한 C0008 결과를 같은 명령으로 다시 실행해 확인했다.
펌웨어 바이너리 SHA-256까지 일치했다.

사용자가 MILESTONE-Core Worker를 배포했다. 배포 직후 `/v3/artwork`는 정상이었다.
반면 `/v1/lyrics`는 있는 곡과 없는 곡 모두 502였다.

- 원인: LRCLIB 요청의 `redirect: "error"` 옵션.
- 수정: `redirect: "manual"`로 바꾸고, 실패 원인을 알려주는 짧은 진단 헤더를 추가했다.
- 재배포 후 운영 서버에서 200·204가 정상으로 나오는 것을 확인했다.

1. **C0008 재실행**
   - `firmware.sh`, `run.sh`, `preview.sh`, `node --check app.js`를 다시 돌렸다.
   - Worker `node --test`를 다시 돌렸다.
   - 로컬 Node에서 실제 LRCLIB으로 `/v1/lyrics`를 호출했다.
   - 저장 보호(`LyricsSave`)와 App 조회 조건 코드를 직접 읽었다.
2. **1차 배포 후 운영 확인**
   - `/v3/artwork`: 200 image/jpeg, SOF0 200×200.
   - `/v2/artwork`: 200, MAB1 1,464 B.
   - `/v1/lyrics`: 모든 요청 502. 응답 시간이 `/health`와 같은 0.4~0.6초 수준이었다.
3. **원인 판단**
   - Cloudflare Workers의 `fetch`는 `redirect`로 `follow`/`manual`만 받는다고 판단했다.
   - Node 기반 로컬 테스트는 `error`를 지원해 이 문제를 잡지 못했다.
   - 재배포 후 정상 동작으로 이 판단을 확인했다.
4. **수정** (`MILESTONE_Core/services/artwork-worker/src/lyrics.js`)
   - `redirect: "manual"`. 3xx는 기존 "200이 아니면 실패" 경로로 거절한다.
   - 502 응답에 `X-Milestone-Upstream` 진단을 붙인다.
     - 값 예: `lrclib-<status>`, `lrclib-body`, `lrclib-invalid-lrc`, `fetch-<ErrorName>`.
     - 가사 본문은 넣지 않는다.
   - 진단은 캐시하지 않는다.
5. **테스트**
   - 기존 redirect 기대값을 `manual`로 바꿨다.
   - 403, 301, fetch 예외 진단 헤더와 비캐시 재시도 테스트를 추가했다.
