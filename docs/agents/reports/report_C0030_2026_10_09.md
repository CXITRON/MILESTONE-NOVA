## Title

바이너리 수신·512 KiB 협상·CRC와 SD 대기 축소 및 0.1.16 OTA 배포

## Summary

사용자가 변환 속도는 양호하나 전송이 느리다고 알리고 여러 적절한 개선을 요청했다.
WebServer의 바이트 단위 multipart 검사 경로를 피하는 raw body 수신, 최대512 KiB
전송 단위 협상, 테이블 CRC, 시간 기준 SD 양보를 구현했다. 기존 자료·클라이언트·
이어받기·CRC·저장 확정 계약을 유지했다. 0.1.16을 커밋·푸시·정식 게시하고 공개 자산을
재검증했다. 현재 원격 작업으로 시리얼을 사용할 수 없어 실제 기기 처리량은 미측정이다.

## Work Performed

### 수신과 전송 단위

- `/api/transfer` begin에 `chunkBytes`(최대524288), `rawChunks:true`를 광고한다.
- 광고가 있을 때만 브라우저는 `/api/blob/raw`에 octet-stream Blob을 보낸다.
  이는 설치된 SDK의 bulk read 경로를 사용한다. 광고 없는 구형 기기는 기존 multipart다.
- IndexedDB의256 KiB 단위/schema는 유지한다. 임의 durable offset부터 여러 저장 블록을
  합쳐 전송하여 기존에 준비한 자료도 재변환 없이 이어 보낼 수 있다.
- Portal PSRAM512 KiB+1 할당 실패 시256 KiB+1로 낮춰 광고한다. 수신 한도는 Files.h 상수를 사용한다.
- raw 경로도 AP token/Host/Content-Type을 확인하고 초과·중단 요청을 거절한다.
  SDK가 raw/multipart에 같은 callback을 사용하므로 Content-Type 검사 후 raw descriptor에 접근한다.

### CRC와 SD

- C++ CRC32와 Formats의 incremental CRC를 하나의 constexpr256-entry table로 처리한다.
  reflected polynomial/init/final 계약은 유지한다. JS도 table/indexed loop를 사용한다.
- SD는32 KiB batch로 쓰고 작업 경과4ms 이상이면1tick을 양보한다.
  이는 단일 SD 쓰기나flush 자체를4ms 이내로 제한하는 hard deadline은 아니다.
- 데이터flush와 atomic checkpoint 성공 뒤에만 ACK한다. 수신·SD 동시 파이프라인은
  도입하지 않았으며 기존 순서·중복 검사·durable offset은 유지한다.

### 진단과 범위

- chunk 응답과 USB UPLOAD 로그에 receiveMs/verifyMs/writeMs를 기록한다.
  각각 본문 수신/RAM CRC/신규 SD 쓰기+checkpoint 비용이다. 중복 요청의 SD 재읽기,
  작업 대기열, 전체 HTTP RTT는 이 수치에 포함되지 않아 별도로 비교해야 한다.
- 변환 방식/해상도/FPS/화면렌더/LCD/LED/핀맵/SD클럭은 바꾸지 않는다.
  공유 CRC 교체는 기존 미디어 검증에도 적용되지만 형식·재생 알고리즘은 유지한다.

## Issues / Limitations

- 큰chunk만으로 속도가2배라고 보장하지 않는다. Wi-Fi·SD·전송량에 따른 실측이 필요하다.
- raw callback은 실제 SDK로 컴파일·검토했지만 실물 HTTP 수신은 아직 미검증이다.
- PSRAM 사용은 최대256 KiB 늘며 할당 실패 fallback을 둔다.
- LED 간헐 점멸은 기존 사용자 수용 상태다. RF 설정/WebCodecs/변환 구조는 변경하지 않았다.
