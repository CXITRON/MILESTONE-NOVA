## Title

바이너리 수신·512 KiB 협상·CRC와 SD 대기 축소로 업로드 전송 개선

## Summary

사용자가 변환 속도는 양호하나 실제 전송이 느리다고 알리고 여러 적절한 개선을 요청했다.
현재 WebServer multipart parser가 본문을 한 바이트씩 검사하는 경로를 확인하여,
SDK의 raw body bulk-read 경로를 사용하는 application/octet-stream endpoint를 추가했다.
최대512 KiB 협상, CRC table, 시간 기준 SD 작업 양보를 적용하고 기존 클라이언트와
IndexedDB 자료/재전송/이어받기/저장 확정 계약을 유지했다. 로컬0.1.16 빌드·서명 준비 완료.
기기 전송 처리량은 아직 실측하지 않았다.

## Work Performed

### 바이너리 경로와 전송 단위

- /api/transfer begin에 chunkBytes(최대524288)와rawChunks=true를 광고한다.
- 브라우저는 광고된 기기에서만 /api/blob/raw와Blob body를 사용한다.
  광고가 없는 구형 기기는256 KiB multipart /api/blob를 사용한다.
- IndexedDB 저장 단위256 KiB와schema는 유지한다. 임의 durable offset부터 최대512 KiB를
  모아 전송하므로 기존 준비 자료도 재변환 없이 이어 보낼 수 있다.
- Portal PSRAM buffer512 KiB+1을 할당하되 실패 시256 KiB+1로 낮춰 광고한다.
  Storage/Portal의 허용량은 Files.h의상수를 사용한다.
- RAW_START에서 AP token/Host/Content-Type을 확인하고, 초과/중단 요청은 저장하지 않는다.
  SDK는 raw/multipart에 같은 upload callback을 사용하므로 raw() 접근 전에 Content-Type을
  검사하여 multipart descriptor를 raw로 잘못 역참조하지 않는다.

### CRC와 SD

- C++ Text의공유 crc32Update/CRC32를 constexpr256-entry table로 바꾸고 Formats의
  incremental API도 이를 사용한다. reflected polynomial/init/final 계약은 그대로다.
- JS도 table 및 indexed loop를 사용한다. 준비·업로드·source identity의 CRC 값은 유지된다.
- SD는32 KiB batch로 쓰고 작업 경과4ms 이상일 때1tick을 양보한다. 이전8 KiB마다
  무조건1tick을 더하는 방식과 구분한다. 단일 SD 쓰기/flush/checkpoint 자체의 hard deadline은 아니다.
- chunk ACK는 데이터flush와기존 atomic checkpoint가 성공한 뒤에만 반환한다.
  동시 요청/수신·SD 파이프라인을 도입한 것은 아니며 순서와 durable offset은 유지한다.

### 진단과 범위

- chunk 응답과 USB UPLOAD 로그에 receiveMs/verifyMs/writeMs를 기록한다.
  이는 각각 raw/multipart body 수신, RAM CRC, 신규 SD 쓰기+checkpoint 비용이다.
  중복 요청의 SD 재읽기/대기열/전체 HTTP RTT는 별도로 측정해야 한다.
- 변환 방식/해상도/FPS/화면렌더/LCD/LED/핀맵/SD클럭은 변경하지 않는다.
  공유 CRC 구현 교체는 기존 미디어 검증에도 적용되지만 형식/재생 알고리즘은 유지한다.
