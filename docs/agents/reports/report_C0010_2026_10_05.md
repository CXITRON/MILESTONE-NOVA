## Summary

Claude Code가 남긴 변경과 진단 로그를 보존한 상태에서 Codex가 후속 수정을 완료하고
유선 연결된 ESP32-S3 기기에 업로드했다. 같은 곡의 SD 재읽기가 다시 HTTP 조회를
시작하던 루프를 차단했고, 재읽기 중에는 기존 아트/가사를 유지한다. 버튼은 5ms 간격의
독립 task에서 취득해 화면 렌더가 늦어져도 짧은 입력을 큐에 보관한다.
일본어 글꼴과 저장된 부팅 문구·색상도 적용했다.

펌웨어 빌드, 전체 호스트 검사와 실제 C++ renderer 67장 검사가 통과했다.
1차 수정 이미지의 180초 BLE/SD 로그에서 곡 정보 5개와 아트 저장 후 재읽기 2회를 확인했고,
기존의 연속 revision 증가 루프는 관찰되지 않았다. 마지막 보강을 포함한 최종 이미지를
다시 업로드하고 100초 동안 Wi-Fi/SD와 입력 큐 상태를 확인했다.

OTA 코드는 호스트에서 수신·오류·취소·시간 제한·부팅 확정을 검사했다. 그러나 연결된
기기는 암호와 RSA 공개키가 미설정이고 공개 업데이트 manifest도 HTTP 404다.
실제 무선 설치와 rollback 성공을 확인한 것은 아니다. 이 보고서의 Completed는
이번 직접 지시의 수정·조사·보고 완료를 뜻하며 U0001 전체 완료를 뜻하지 않는다.

### 1. 같은 곡의 아트/가사 깜빡임

Claude의 로그에서는 동일 track key, 동일 session generation에서 asset revision만
약 4초마다 증가했고, 각 SD 읽기 결과는 `art=1 lyrics=1 error=0`이었다.
SD 디코딩 실패로 인한 반복이 아니라 다음 App 상태 처리의 결합이었다.

1. SD 요청을 큐에 넣으면 `assetsNeeded_`가 false가 된다.
2. 아트 자동 조회 조건에는 진행 중 SD 요청인 `assetPending_` 확인이 빠져 있었다.
3. revision 갱신마다 표시 버퍼와 재시도 상태를 지워 SD 읽기 동안 새 HTTP 조회를 시작했다.
4. 같은 아트를 다시 저장하면서 revision을 올렸고, 존재하지 않는 `.missing` 삭제도
   추가 revision을 발생시켰다.

`TrackAssets`에 실제 App의 자산 상태를 모으고 SD 읽기가 끝나기 전에는 아트와 가사
조회 모두 대기하도록 했다. 같은 곡의 revision 갱신은 표시 중인 버퍼를 유지하고,
새 곡 전환 또는 성공한 읽기에서 부재가 확인될 때만 이전 내용을 비운다.
읽기 오류가 나면 마지막으로 정상 표시한 내용을 유지한다.

자동 revision 갱신은 아트의 60초 재시도 간격과 가사의 곡별 조회 여부를 초기화하지 않는다.
명시적인 재조회 명령은 다시 시도할 수 있다. 없는 파일의 단순 삭제는 revision을
올리지 않지만, 없는 이미지에 새 `.missing` 차단 표식을 만든 경우는 한 번 갱신한다.

### 2. 가사 화면과 렌더 지연 중 버튼 누락

기존 버튼 샘플링은 App 루프에 묶여 있어 렌더/작업 사이에 눌렀다 놓은 입력을
아예 관찰하지 못할 수 있었다. GPIO 읽기와 기존 debounce/long/repeat 판정을
priority 2, 2 KiB stack의 `nova-input` task로 옮겼다.

- 5ms마다 5개 버튼을 취득하고 32개 고정 큐에 보관한다.
- 반복 입력은 같은 키의 대기 repeat를 합치고, 큐 절반부터 추가 repeat를 제한한다.
  가득 찬 큐에서는 repeat를 먼저 제거해 MENU/BACK/OK와 같은 개별 입력 공간을 확보한다.
- task는 UI/설정/SD를 만지지 않는다. 짧은 critical section으로 큐만 보호하고,
  App이 기존 입력 처리 경로로 소비한다.
- task 생성 실패는 기존 polling으로 동작하며 로그로 알린다. 실제 개별 입력이
  큐 포화로 누락되면 `MEM` 로그의 `input_dropped`에 기록한다.

이 수정은 샘플링 누락을 방지하는 것이다. 렌더 자체의 소요 시간이나 화면 반응 지연을
0으로 만든 것은 아니다. 실물 관찰 중 카운터는 0이었지만 물리 버튼을 직접 누른 시험은 아니다.

### 3. 일본어 가사와 혼합 문자열

기존 Unifont Korean2를 유지하고 Japanese3를 추가했다. 가나·한자는 일본어 글꼴을
우선 선택하며, 한글·영문은 기존 글꼴을 우선한다. 폭 측정·줄바꿈·실제 그리기·marquee가
같은 glyph 선택 함수를 사용한다.

Japanese3에 없는 반각 가나는 표시할 때 대응 전각 문자로 변환한다. 원본 가사,
메타데이터와 track key는 변경하지 않는다. 제공 글꼴에 없는 희귀 한자/이모지는 `?`로 표시된다.
추가 폰트 데이터는 149,411 bytes이며 최종 펌웨어는 6 MiB 앱 파티션 안에 들어간다.

### 4. 저장한 부팅 문구

부팅 View에 NVS에서 읽은 설정을 연결하고 UI에 하드코딩되어 있던 “오늘도 한 걸음”을
`settings.message`와 `messageColor`로 바꿨다. 빈 문구도 그대로 존중하며, 두 줄 이상을
표시할 여유 높이를 확보했다. 포털 문구 설명에도 부팅 화면에 사용됨을 반영했다.

### 5. OTA 확인

- 실제 기기의 `status`가 `Set password + RSA key`를 반환했다. `ota` 요청도 수신 창을
  열지 못했고 `ota-close`로 마무리했다. 저장된 자격증명을 임의로 교체하지 않았다.
- 설정된 공개 manifest URL
  `https://raw.githubusercontent.com/CXITRON/MILESTONE-NOVA/main/releases/stable.json`은
  읽기 전용 조회에서 HTTP 404였다. 릴리스 게시나 서명 키 설정을 대신 수행하지 않았다.
- Arduino ESP32 3.3.11의 사용 중 qio_opi SDK에서
  `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=1`을 확인했다.
- 실제 `src/network/Ota.cpp`를 컴파일하는 host 검사를 추가했다. OpenSSL로 실제 공개키를
  읽되 transport/flash/task/시계는 adapter로 대체한다. 기존 별도 서명 검사는 RSA-2048/4096,
  잘못된 키·변조 거절과 실제 빌드 이미지 descriptor를 확인한다.
- 기기 암호/공개키 프로비저닝 후 로컬 signed OTA를 시험할 수 있다. 인터넷 자동 확인/다운로드는
  별도로 유효한 manifest와 서명 이미지 게시가 필요하다.

### 연결 기기

- USB: `/dev/ttyACM0`, ESP32-S3 revision v0.2, 240MHz, 내장 PSRAM 8MB.

  PSRAM free 6,694,740 bytes, loop 최대 239,152µs, `input_dropped=0`.
- **최종 이미지 100초 (09:47:36–09:49:16 KST):** upload exit 0/flash hash 검증 후

## Issues / Limitations

- 물리 버튼 조작과 LCD 육안 확인은 수행하지 않았다. host 지연 입력 검사는 실제 GPIO bounce,
  조작감, 패널 tearing까지 증명하지 않으며 입력 카운터 0도 이를 대신하지 않는다.
- 180초 BLE 관찰은 재시도/삭제 marker의 마지막 보강 전 이미지
  (`88d7a8f1a55976f66a5faa50fae29232fa2cfeaca77a43c3e9083c3adf687b94`)였다.
  최종 보강은 전체 host 검사를 다시 통과하고 별도 USB/100초 관찰로 확인했다.
- OTA 미설정과 manifest 404를 확인했으며 실제 무선 설치·부팅 확정·rollback은 미검증이다.
- 수분간 로그는 24–72시간 soak, SD 제거/불량, RF 단절, 전원 차단 검증을 대체하지 않는다.
