# Request U0001

- **Request ID:** U0001
- **Priority:** H
- **Date:** 2026-09-23
- **Status:** In Progress

## Title

신형 MILESTONE 탁상형 기기용 독립 펌웨어 아키텍처 설계 및 구현

## Summary

본 요청은 기존 MILESTONE 펌웨어를 READ-ONLY 참고자료로 분석한 후, LOLIN S3 Pro 기반 단일 ESP32-S3 하드웨어를 대상으로 신형 MILESTONE 탁상형 기기용 펌웨어를 clean-slate 방식으로 신규 설계·구현하는 업무이다.

기존 펌웨어의 기능 사양, 사용자 경험, 문제 해결 기록 및 유효한 구현 개념은 참고하되, 기존 저장소 구조·MAIN/ZERO 듀얼보드 구조·보드 간 SPI 통신·과거 핀맵·레거시 하드웨어 계층·임시 workaround·구조적 부채 및 `.inc` 중심 단순 분리 구조는 신규 프로젝트에 종속시키지 않는다.

신규 펌웨어는 240×320 ST7789V 디스플레이, RTC, 환경 센서, 배터리 관리, microSD, Wi-Fi, BLE, OTA, NOW 음악 화면, 앨범아트 및 실시간 동기화 가사를 포함하는 독립적인 장시간 운용 펌웨어를 목표로 한다. 기능 수보다 안정성, 유지보수성, 사용자 경험 및 실제 하드웨어 운용 가능성을 우선한다.

## 0. 가장 중요한 프로젝트 원칙

새 펌웨어는 **clean-slate 방식**으로 설계한다.

기존 프로젝트의 다음 요소는 신규 프로젝트에 그대로 계승하여서는 안 된다.

- 기존 디렉터리 구조
- 기존 MAIN/ZERO 듀얼보드 구조
- 보드 간 SPI 통신 구조
- 과거 핀맵
- 과거 하드웨어 abstraction
- 과거 임시 workaround
- 이미 폐기된 기능
- 기존 코드의 구조적 부채
- 기존 `.inc` 중심 단순 분리 구조
- 과거 watchdog / heap / panic 문제를 유발할 가능성이 있는 구조

다만 기존 MILESTONE 펌웨어 파일은 반드시 선행 분석하여야 한다.

기존 펌웨어는 새로운 프로젝트의 기반 코드가 아니라 다음의 참고자료로 사용한다.

- 기능 사양
- UX 참고자료
- 기존 문제 해결 기록
- 기존 구현에서 유효했던 동작 방식
- 기존 실패 사례와 회피해야 할 구조

기존 코드에서 확인할 것:

1. 기존에 실제 구현된 기능
2. 화면 종류와 UI 흐름
3. 버튼 UX
4. NOW 음악 화면
5. BLE 미디어 메타데이터 처리
6. 앨범아트 처리
7. 미디어/영상 관련 기능
8. microSD 파일 구조
9. 설정 저장 방식
10. RTC
11. 센서
12. 배터리 표시
13. D-Day
14. 시계
15. 집중 타이머
16. OTA
17. Wi-Fi
18. Deep Sleep 또는 전원 UX
19. 기존 boot splash
20. 오류 처리
21. serial log 구조
22. 장시간 실행과 관련된 기존 문제
23. 사용자가 실제로 유지할 가치가 있는 UX

기존 코드에서 좋은 아이디어나 동작은 참고할 수 있다.

그러나:

- 기존 코드를 단순 복사·붙여넣기 방식으로 이식하여서는 안 된다.
- 신형 하드웨어에 부합하지 않는 코드는 이식하여서는 안 된다.
- 기존 버그 및 결함을 신규 구조에 재현하여서는 안 된다.
- 신규 프로젝트에 불필요한 legacy dependency를 생성하여서는 안 된다.
- 새 저장소는 기존 저장소 없이도 독립적으로 빌드되어야 한다.
- 기존 펌웨어는 **READ-ONLY 참고자료**로 취급한다.

작업 시작 후 먼저 기존 펌웨어 분석 결과와 새 프로젝트 아키텍처 계획을 작성한 뒤 구현에 들어가라.

사용자의 승인 대기를 위해 중단할 필요는 없다.  
명백한 하드웨어 정보가 부족한 경우를 제외하고는 합리적인 기술적 판단에 따라 작업을 계속 진행하여야 한다.

## 2. DISPLAY

### Display

- ST7789V
- 2.0 inch
- 240 × 320
- RGB565
- SPI
- MISO 미사용

### 최종 LCD GPIO

- DIN / MOSI = GPIO6
- SCK = GPIO7
- CS = GPIO15
- RST = GPIO16
- D/C = GPIO17
- BL = GPIO18

GPIO18은 LCD backlight PWM 제어에 사용한다.

LCD 배선 길이는 일부 약 10 cm 정도가 될 수 있다.

따라서:

- 초기 구현에서 최고 SPI clock을 일률적으로 강제하여서는 안 된다.
- 안정성을 우선하여 적절한 기본 SPI clock을 선정하여야 한다.
- 설정을 통하여 SPI frequency를 변경할 수 있는 구조를 고려하여야 한다.
- 실제 하드웨어 검증 결과에 따라 clock을 상향 조정할 수 있도록 구조화하여야 한다.

240×320 해상도를 적극적으로 활용한다.

기존 128×160 화면을 단순 확대하는 방식으로 구현하여서는 안 된다.

신규 240×320 화면에 맞추어 다음 요소를 재설계하여야 한다.

- typography
- margin
- information hierarchy
- icon size
- text wrapping
- album artwork
- progress bar
- lyrics

## 4. DEEP SLEEP / POWER UX

물리적인 전원 스위치는 사용하지 않는다.

Deep Sleep을 사용자 관점에서 **OFF 상태**로 사용한다.

### Deep Sleep wake

- GPIO5 OK 버튼

GPIO39 / GPIO40 / GPIO41 / GPIO42는 Deep Sleep wake source로 사용하지 않는다.

Sleep 진입 과정:

1. 필요한 설정 저장
2. 파일 flush
3. microSD 작업 종료
4. LCD backlight OFF
5. external RGB OFF
6. RED status LED OFF
7. GREEN status LED OFF
8. 필요한 peripheral 종료
9. GPIO5 wake source 설정
10. Deep Sleep 진입

Wake 후:

- 안정적인 boot / resume UX 제공
- wake를 발생시킨 버튼 눌림이 UI 입력으로 중복 처리되지 않게 고려

## 8. STATUS LEDs

두 개의 일반 2핀 LED가 추가된다.

### RED

- GPIO1
- GPIO1 → 1kΩ → RED LED → GND

### GREEN

- GPIO8
- GPIO8 → 1kΩ → GREEN LED → GND

PWM brightness control 가능.

### GREEN LED 역할

- 정상 상태
- heartbeat
- device alive indicator

평상시에는 너무 빠르게 깜빡이지 말고 천천히 밝아졌다 어두워지는 **breathing heartbeat** 효과를 사용한다.

### RED LED 역할

- warning
- critical error
- low battery
- SD failure
- OTA failure
- fatal configuration issue 등

정상 상황에서는 RED OFF.

RED / GREEN 상태 표현은 별도의 Status LED manager를 통하여 관리하여야 한다.

UI thread/task를 blocking하는 `delay()` 기반 효과는 사용하여서는 안 된다.

## 12. NOW MUSIC MODE

NOW는 주요 화면 중 하나다.

가능한 정보:

- title
- artist
- album
- playback state
- elapsed time
- duration
- progress
- album artwork
- connection state
- lyrics

기존 MILESTONE 펌웨어에서 기존 NOW 화면 및 미디어 정보 수신 방식을 분석한다.

단 새 구현에서는 ESP32-S3 특성을 따른다.

ESP32-S3는 Bluetooth Classic을 지원하지 않으므로 새 설계가 Classic Bluetooth 전제를 가지지 않도록 한다.

BLE만으로 구현 가능한 범위와 스마트폰 companion/helper가 필요한 범위를 명확히 분리하여야 한다.

미디어 메타데이터 일부가 누락되어도 화면 전체가 깨지지 않도록 한다.

예:

- title 없음
- artist 없음
- album artwork 없음
- duration 없음

각 상황에 fallback을 제공한다.

## 13. REAL-TIME LYRICS

NOW 화면에 실시간 동기화 가사 기능을 넣는다.

핵심 동작:

현재 playback position을 기준으로 해당 timestamp의 가사를 표시한다.

기본 UI 개념:

```text
--------------------------------
NOW              02:14 / 03:51

       previous lyric

       CURRENT LYRIC
       CURRENT LYRIC

          next lyric

--------------------------------
Artist
Title
████████●────────
--------------------------------
```

이 레이아웃을 그대로 복제할 필요는 없다.

240×320 화면의 가독성과 정보 밀도를 고려하여 적절한 방식으로 설계하여야 한다.

가사 UI 요구사항:

- current lyric 가장 강조
- previous lyric 덜 강조
- next lyric 덜 강조
- 긴 문장 wrap
- 한글 지원
- 영어 지원
- 한글 / 영어 혼합 지원
- 화면 밖 overflow 방지
- pause 처리
- seek 처리
- resume 처리
- track change 처리
- instrumental 처리
- lyrics unavailable 처리
- unsynced lyrics 처리

가사 줄 변경 시 화면 전체를 반복적으로 full redraw하여 깜빡임이 발생하지 않도록 구현하여야 한다.

가능하면 다음을 고려한다.

- smooth vertical movement
- fade
- partial redraw

하지만 효과보다 안정성을 우선한다.

## 14. LYRICS ARCHITECTURE

가사 획득과 표시 로직을 반드시 분리한다.

역할 예:

- LyricsProvider
- LyricsParser
- LyricsTimeline
- LyricsCache
- LyricsRenderer

정확한 클래스명은 자유지만 역할은 분리한다.

최소 지원:

1. microSD local LRC
2. line-synced lyrics

예:

```text
[00:12.40]First lyric
[00:16.85]Second lyric
[00:21.20]Third lyric
```

LRC parser에서 고려:

- minutes
- seconds
- centiseconds / milliseconds
- multiple timestamp tags
- offset tag
- metadata tags
- CRLF / LF
- malformed line
- UTF-8
- Korean text
- duplicate timestamp
- empty lyric
- instrumental section

corrupted LRC 때문에 시스템 전체가 죽지 않도록 한다.

## 15. LOCAL LYRICS STORAGE

microSD에 lyrics cache/storage 구조를 만든다.

곡 식별에 다음을 고려한다.

- artist
- title
- album
- duration
- 또는 안정적인 hash

파일명에 사용할 수 없는 문자는 sanitize한다.

예:

```text
/lyrics/
    <track-key>.lrc
```

또는 더 나은 구조를 설계해도 된다.

동일 곡이 다시 재생되면 네트워크 요청 전에 local cache를 우선 사용할 수 있도록 한다.

## 16. FUTURE ONLINE LYRICS PROVIDER

처음부터 외부 lyrics provider를 추가할 수 있는 구조로 만든다.

중요:

- 전체 구조를 특정 웹사이트의 HTML scraping 방식에 종속하여서는 안 된다.
- API key를 source에 hard-code하여서는 안 된다.
- endpoint 정보를 여러 파일에 분산하여 관리하여서는 안 된다.
- credentials는 config / secrets와 분리한다.
- provider failure가 NOW 전체를 죽이지 않아야 한다.
- local LRC는 인터넷 없이도 동작해야 한다.
- 저작권 보호된 가사 텍스트를 firmware source에 직접 넣지 않는다.

## 17. LYRIC PLAYBACK SYNCHRONIZATION

가사 동기화는 `delay()` 기반으로 구현하여서는 안 된다.

다음 상태를 관리한다.

- track identifier
- current playback position
- track duration
- play / pause
- last authoritative position
- last synchronization timestamp
- current lyric index

재생 위치 정보가 매 순간 들어오지 않는 경우:

```text
estimatedPosition =
lastReceivedPosition +
elapsedSinceLastSync
```

방식으로 로컬 추정한다.

단:

- PAUSE 상태에서는 증가하지 않아야 한다.
- SEEK 발생 시 즉시 재동기화한다.
- 새로운 authoritative position이 오면 drift를 보정한다.
- track change 시 모든 lyric timeline state를 reset한다.

매 frame마다 가사 전체 배열을 처음부터 선형 검색하는 방식은 사용하여서는 안 된다.

다음 중 적절한 방법을 사용한다.

- current index tracking
- binary search
- hybrid

## 21. 기존 `.inc` 단순 분리 구조 폐기

기존 MILESTONE 펌웨어에서 사용하던 **“.inc 파일로 구현 코드를 단순히 분할하여 include하는 방식”**은 신규 프로젝트의 기본 구조로 계승하여서는 안 된다.

단순히 하나의 거대한 프로그램을 여러 `.inc` 파일로 잘라놓는 것은 **모듈화로 간주하지 않는다.**

새 프로젝트에서는 기능별 책임과 인터페이스를 기준으로 실제 C++ 모듈로 분리한다.

권장 형태:

```text
include/
    BoardConfig.h
    ...

src/
    main.cpp
    display/
    ui/
    input/
    media/
    lyrics/
    storage/
    sensors/
    power/
    network/
    ...
```

각 subsystem은 필요에 따라:

```text
Foo.h
Foo.cpp
```

형태로 구성한다.

원칙:

- `.h`에는 interface / type / declaration 중심
- `.cpp`에는 implementation
- 구현 코드를 `.h`나 `.inc`에 대량으로 넣지 말 것
- 다른 `.cpp`를 include하지 말 것
- `.inc`를 단순 코드 조각 분할 목적으로 사용하지 말 것
- global symbol과 cross-module dependency를 최소화할 것
- 각 subsystem의 public interface를 명확하게 만들 것
- circular dependency를 피할 것
- shared state를 include 파일을 통해 암묵적으로 공유하지 말 것

`.inc` 파일이 정말 필요한 경우는 다음처럼 명확한 이유가 있을 때만 제한적으로 허용한다.

- 컴파일 타임 생성 데이터
- 정적 asset table
- 자동 생성 리소스

기존 펌웨어의 `.inc` 파일들은 먼저 분석하여 각 코드가 실제로 어떤 책임을 가지는지 파악한 뒤, 새 프로젝트에서는 적절한 `.h` / `.cpp` module로 재설계한다.

기존 `.inc` 파일 이름이나 분할 단위를 그대로 따라갈 필요가 없다.

기능별 책임과 의존성을 기준으로 모듈 경계를 새로 판단하여 구조화하여야 한다.
