## Summary

Claude Code가 추가한 NOW 레이아웃 5와 온라인 가사 클라이언트를 이어받아, 누락된

아티스트/앨범을 두 줄로 나누며, 원본·캐시의 200×200 규격은 유지한다.
새 통합 화면은 아트·음악 정보·동기화 가사·진행 바를 함께 표시한다.

ESP32 빌드, 전체 호스트 검사, 63개 화면 렌더, Worker 가사 11개·기존 아트워크
22개 검사, Wrangler 번들을 통과했다. 실제 LRCLIB에서 받은 LRC를 로컬 Worker로
검증·반환하고 캐시 재사용까지 확인했다. **공개 Worker 배포와 기기 업로드는 하지 않았다.**

이 보고서의 Completed는 이번 추가 구현·검증 작업에 대한 상태다. U0001 전체는

### Worker 온라인 가사 API

- 수정 위치는 실제 서비스가 있는 형제 저장소
  `/run/media/citron/T7/Documents/Dev/MILESTONE_Core/services/artwork-worker`다.
  NOVA 내부 `MILESTONE_Legacy`와 옛 기기 펌웨어는 수정하지 않았다.
- `POST /v1/lyrics`는 form의 `title`·`artist`와 선택적 `album`·초 단위 `duration`을 받는다.
  LRCLIB `/api/get`만 호출하며 title/artist의 정규화 일치와 알려진 재생 길이 ±2초를 확인한다.
  `plainLyrics`나 추측 검색 결과를 동기화 가사로 전달하지 않는다.
- 잘못된 UTF-8/percent encoding, 중복 필드, 제어 문자, 초과 입력을 거절한다.
  form 1400 bytes, 각 정규화 문자열 192 codepoints, JSON 256 KiB, LRC 32 KiB로 제한한다.
  LRC의 timestamp/line/entry/offset도 기기 parser의 지원 범위로 검증한다.
- 정상 LRC는 200, 일치하는 동기화 가사 없음은 204, provider 오류는 502/504,
  cooldown/queue 초과는 `Retry-After`가 있는 503이다. 아트워크 route는 그대로 유지한다.
- 입력 body 읽기는 3초, provider 조회는 대기열/응답 body를 포함해 6초 제한이다.
  isolate별 활성·대기 합계 4개 상한과 250ms 간격을 두고 429의 `Retry-After`를 따른다.
  cooldown을 edge cache에도 기록하지만 여러 Cloudflare 위치 전체를 하나의 전역
  rate limit으로 조정하는 구조는 아니다.
- 정상 응답 30일, 미발견 1시간을 Cache API에 보관한다. 정규화된 곡 정보와 duration을
  SHA-256 key에 포함한다. 502/504를 미발견으로 캐시하지 않으며 cache 장애 시 조회를 계속한다.
- 새 API key, 유료 binding, dependency, LRCLIB 게시 요청은 추가하지 않았다.

### NOVA 클라이언트와 저장·서비스 경계

- 로컬 자산 읽기가 끝난 후에만 온라인 가사를 요청한다. `lyrics_view`와 Wi-Fi/모드/전원
  상태를 검사하며 `artwork_auto` 설정과 독립적으로 동작한다. 자산 읽기당 한 번 요청한다.
- 최대 32 KiB LRC를 service worker에서 파싱하고, 완성된 `Lyrics`를 PSRAM에 보관한 뒤
  해당 곡의 generation에만 전달한다. 파싱 작업을 UI 수신 경로에서 수행하지 않는다.
- HTTP 오류, 초과 크기, 미완료 body, NUL/잘못된 UTF-8, 순수 텍스트, 손상/잘린 LRC를
  거절한다. duration은 64비트로 계산해 덧셈 overflow를 막고 알 수 없으면 보내지 않는다.
- 가사 HTTP timeout은 8초이며 기존 다른 호출의 기본값 4초는 유지한다. 전체 경과 시간
  15초 검사를 body read 사이에 둔다. 이는 진행 중인 blocking read를 즉시 끊는 절대
  15초 보장이 아니며, 종료에는 transport timeout과 SD 작업 시간이 더해질 수 있다.
- `FileOp::LyricsSave`는 `/lyrics/<16자리 소문자 hex>.lrc`만 받는다. 단일 SD writer에서
  기존 파일을 다시 확인한 후 원자 저장하므로, 조회 중 들어온 로컬 파일을 덮어쓰지 않는다.
  빈 로컬 파일도 사용자 선택으로 우선한다. 일반 저장 실패나 SD 없음은 RAM 표시로 처리한다.
- 이전 곡의 응답을 현재 곡에 적용하지 않는다. 조회 중 다음 곡 요청이 들어와도 다음 요청을
  유지한다. 앞선 아트 HTTPS 처리 중 AP/OFF가 요청되면 뒤이어 새 가사 조회를 시작하지 않는다.
- 설정 구조와 NVS schema는 변경하지 않았으며 `now_layout` 유효 범위만 0..5로 확장했다.

### 화면과 긴 문자열

- 레이아웃 0/3은 172×172 아트와 제목·아티스트/앨범 두 줄을 사용한다. 200×200
  원본과 캐시를 유지해 표시 때 축소한다. 통합 레이아웃 5는 88×88 아트와 음악 정보,
  이전/현재/다음 가사 및 진행 바를 표시한다.
- 음악 정보의 marquee는 기존 `Canvas::marquee`를 연결한 것이다. `scroll` ON일 때
  영역보다 긴 제목/아티스트/앨범이 양 끝에서 2초씩 멈추며 왕복한다(기본 24 px/s).
  모든 문구가 가로 이동하는 것은 아니다. 큰 글씨 레이아웃과 가사는 wrap/clip 경로를 사용한다.

## Issues / Limitations

- 공개 `/v1/lyrics`는 **미배포**다. 실제 LRCLIB 조회 성공은 로컬에서 실행한 Worker의
  결과이며 Cloudflare 배포 후 네트워크/캐시/운영 검증을 대신하지 않는다.
- Worker 배포 시 C0007의 `/v3/artwork` JPEG 200×200 전환도 함께 나간다. 옛 MAC1 전용
  기기와의 호환 파괴는 이전 사용자 선택이며 이번 가사 작업에서 새로 결정한 사항이 아니다.
- LRCLIB에 정확히 일치하는 동기화 가사가 없거나 앱의 metadata가 다르면 204일 수 있다.
  provider 장애/미발견을 자동으로 반복 조회하지 않는다. 곡 재선택이나 포털 재조회로
  자산 읽기를 다시 시작할 수 있다. 로컬 LRC는 인터넷 없이 사용한다.
- ESP TLS/FreeRTOS/SD·NVS/AMS 무선/AP/실제 LCD/전류/장시간 운용은 미검증이다.
  브라우저 포털 상호작용은 이번에 실행하지 않았다. host mock/sanitizer/렌더 통과를
  해당 실물 항목의 성공으로 계산하지 않는다.
- 전체 기능의 실물 동작을 보증하는 보고서가 아니다. 나머지 U0001 검증 범위는
  [기능 대조표](../../design/feature-parity.md)와 [실물 점검표](../../guides/hardware-validation.md)에 유지한다.
