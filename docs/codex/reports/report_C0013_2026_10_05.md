## Title

20 KiB NVS 저장 실패 복구와 Wi-Fi/BLE 부팅 연결 수명주기 보완

## Summary

사용자가 NOVA 0.1.9에서 `Settings save failed (write nvs=126/630 heap=85476)`,
Wi-Fi reason 8/36, 최소 heap 2256 B를 보고하여 LED 효과 확장보다 먼저 처리했다.
사용자는 64 KiB 파티션이 아직 적용되지 않았고 현재 유선 연결이 없다고 확인했다.
설정 저장 시 ESP-IDF 오류를 보존하고 공간 부족일 때만 진단 이력을 회수한다.
Wi-Fi의 실제 연결 손실과 접속 실패/의도적인 연결 해제를 구분하고 부팅 대기 및 재접속 시간을 보완했다.
소스와 호스트 검증까지 완료했으며 실제 기기 문제 해결은 아직 확인하지 못했다.

## Related Requests

- U0001: 장시간 운용 안정성, 설정 보존, Wi-Fi/BLE 동시 운용 관련 직접 후속 지시.
- 선행 LED 효과 확장 지시는 취소되지 않았으며 이번 우선 작업 동안 대기한다.

## Work Performed

## Changes

- `src/settings/Store.cpp`, `Store.h`: 기록 형식과 A/B CRC 검증을 유지하면서 NVS write/commit 오류를 직접 수집한다. 메모리 할당 실패는 ESP_ERR_NO_MEM, 검증 실패는 ESP_ERR_INVALID_STATE로 구분한다. 저장 실패 통계를 초기화하여 오래된 수치를 재사용하지 않는다.
- 설정/자격증명 저장 및 기존 Secrets 마이그레이션에서 **ESP_ERR_NVS_NOT_ENOUGH_SPACE일 때만** `nova-diag`를 비우고 한 번 재시도한다. 일반 I/O/할당 실패는 이력 삭제 대상이 아니다. 설정, Wi-Fi 프로필, BLE 본딩 namespace를 지우지 않는다.
- `src/network/Network.cpp`, `Network.h`: GOT_IP 이후 연결 손실과 접속 실패를 별도 누적한다. 로컬 disconnect 요청에 대응하는 leave 이벤트를 손실로 기록하지 않는다. 연결 제한 시간을 15초에서 30초로 늘리고 IP 연결을 루프에서 관찰한 뒤 2초 유지 시 BLE 초기화를 허용한다. 접속 실패 시에도 무한정 BLE 시작을 막지 않는다.
- 연결 손실 후 재시도 기준 시간을 손실 시점으로 갱신한다. 오래된 최초 접속 시각 때문에 즉시 재시도하던 동작을 막고 기존 BLE 연결 시 60초 이상 backoff 정책을 유지한다.
- `src/app/App.cpp`, `App.h`: 2분 간격 진단 기록에 실제 손실과 접속 실패 각각의 건수/원인 코드를 기록한다.
- `tests/network/test_network.cpp`, 해당 support 및 `tests/test_network.py`: production Network 코드를 실행해 비동기 이벤트 분류, DHCP 대기, 안정화, BLE 재접속 간격, 타임아웃, stop, millis wrap을 검증한다.
- `tests/update/test_firmware.cpp`, `tests/update/support/nvs.h`: 공간 회수 후 설정 저장, 자격증명 보존, 일반 쓰기 실패 시 이력 보존, 회수 후에도 공간이 부족할 때 기존 기록 보존을 검증한다.

## Issues / Limitations

- 유선 포트가 없으며 사용자가 미연결을 확인했다. 플래시 쓰기/재파티션/기기 초기화를 수행하지 않았다.
- 현재 20 KiB NVS의 페이지 단편화와 실제 ESP-IDF 오류 코드는 원본 로그에 없어 확정할 수 없다. 호스트 NVS adapter는 바이트 용량/실패 주입 검증이며 실제 NVS 페이지 GC나 전원 차단을 재현하지 않는다.
- 진단 이력을 지우면 다음 진단 기록 시 RAM에 남은 이력이 다시 저장될 수 있다. 이 회수 경로는 영구적인 NVS 크기 증가를 대체하지 않으며, 공간이 충분하지 않으면 명시적인 저장 실패가 유지된다.
- heap 최소 2256 B와 BLE/RF 영향은 실기 추가 관찰이 필요하다. 연결 타임아웃/초기화 순서 개선을 무선 장애 완전 해결로 주장하지 않는다.
- 표준 앱 OTA는 파티션 테이블을 갱신하지 않는다. 현재 소스의 64 KiB 배치는 앱/otadata 주소도 이동하므로 원격 확장에는 별도 이관 설계가 필요하다. 파티션 테이블 갱신 중 전원 차단은 USB 복구가 필요한 상황을 만들 수 있다.
